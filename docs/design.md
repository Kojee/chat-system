# Design Notes

This document collects the design reasoning behind the project: the target architecture, the implementation choices made in the prototype, and the improvements I would make next. For setup and a high-level overview, see the [README](../README.md).

## Target architecture
### Knowledge Base Service
- Web App where documents composing the model's knowledge base can be uploaded/edited
- When a document is uploaded/modified, its text is split into chunks, embeddings are computed and saved in a vector db
- The vector db is exposed via an MCP server that the agent calls to retrieve documents relevant to the user's message
- Requires authentication
    - Could use a revocable, expiring API key system to safeguard client data access
### User Data Service
- Exposes user data through an MCP server endpoint
- Data is saved in a database accessible only by this service, or it could call endpoints of a larger app, acting merely as an interface for the agent
- Requires authentication
    - Every request must be authenticated against the user who triggered it, to prevent data leaks of other users due to hallucinations/prompt injection of the agent. User data is pre-filtered using the session id of the user who triggered the request, and only then any parameters generated by the agent during the tool call are applied.
    - Besides always including a session id linked to the user, it could use a revocable, expiring API key system to safeguard client data access
### Chat Service
- WebSocket endpoint for sending/receiving chat messages
- Agent graph implemented with a framework e.g. LangGraph
    - Initially, a simple graph with an input step, a step for loading and calling the tools needed for the response, and a step to generate the response should suffice
    - In the future, Human-in-the-loop steps might be needed when the agent cannot satisfy client requests, or when certain actions require manual approval
- Models to represent chats with the client
    - In a first prototype, data could be saved in a normal sql database and loaded entirely into the agent's memory. Once the threshold limit for the chosen model is exceeded, compact the chat to keep it within the predetermined limits
        - Assuming an average chat spans about twenty messages, and each message averages 210 characters, that's about 60 Tokens per message (using OpenAI's tokenizer as reference).
        - Assuming the client opens one chat per day, if we wanted to load all chats from the last month into memory, we'd have a context usage of 36k tokens
        - On modern contexts, which often reach 1M tokens, it would be easily possible to load all chats from the last month into memory, consuming less than a tenth of the context and providing the model with a precise overview of the client's recent issues
        - However, a tradeoff between costs and agent effectiveness must be made
    - If we wanted to load older chats, or if we wanted to reduce memory usage, it might be appropriate to create a vector db parallel to the sql db and set up a RAG system, to quickly retrieve the messages most relevant to the ongoing discussion
        - One could consider a hybrid solution where we fully load the most recent chats into memory, while retrieving the remaining chats of the year with a vector db query, where each chat is tagged with the day it was opened. On the resulting chats, further filter via vector similarity against the messages of the current chat, to retrieve only the most relevant chats. To effectively retrieve chats, one could create a summary of each chat and generate the embedding from that, associating the chat id in a tag. Once the most relevant chats are retrieved, the agent could, through a tool, load them into memory by reading the summary tags, thus having the full content of the old chat.
- Connects to MCP servers to retrieve tools usable during the chat
    - Initially, all MCP servers are made available to the model by adding them to the context
    - Depending on the number of MCP servers, it might be appropriate to implement a progressive discovery flow, allowing the model to discover the tools at its disposal based on the conversation content
        - E.g., an MCP server exposing billing data could be made available only if certain terms are present in the last message sent by the client, e.g., "invoice", "euro", "dollars", "pay", "client"
        - Another alternative is to have a dedicated model that knows all MCP servers and provides them on demand to the main model based on received messages
    - Again, implement metrics to evaluate system performance, to understand which system is best


### Metrics
- Define metrics we want to optimize to evaluate system performance and make the right decisions, especially to understand how to best leverage a potential RAG system
    - Customer satisfaction
    - Total chat cost
    - Memory usage
    - Number of tool calls
    - Number of interrupts, split by interrupt result
- Monitor metrics over time, associating them with a particular state of the deployed system, to build a history of changes and their impacts on system performance
- Such metrics go hand in hand with a careful deployment policy:
    - A system could initially be put into production via canary deployment, thus making it available to a restricted subset of users
    - If the first impressions and metrics calculated on the canary system are better than the main system, the rollout could be gradually extended until it covers 100% of users with the new system
    - Eventually, if we find that the new system does not perform as hoped, we can decide to route requests back to the old system
    - Such a deployment system requires setting up a load balancing infrastructure that knows the main service and the canary one and has a policy for proportional routing of user requests
        - An example could be a reverse proxy implemented via NGINX, where the configuration maps the two routes and defines the policy for splitting requests by percentage across the two servers. The nginx config could be updated incrementally to increase the percentage of requests sent to the canary system. Once the system has been tested, the canary system is promoted to the new production system, and the configuration is reset to send 100% of requests to the main system


### Model provider
Initially we can rely on a provider such as Anthropic/OpenAI, but it should be kept in mind that for a realistic production environment, especially for an assistant that handles sensitive financial data, opting for a sovereign cloud provider with model hosting within the EEA could be a more forward-looking solution:
- User data does not leave the borders of the European Union
- Full control over the lifecycle of collected data
- The data is not used for training new provider models

### Model Tone
Tone and style guidelines live in the system prompt (`chat_backend/config/system_prompt.txt`), stored per agent configuration in `AgentSettings` so they can be versioned and A/B tested alongside the model.

## Implementation choices
### MCP KB Server
The MCP KB service is located in the `mcp_kb_server` folder.
We use Chroma as a vector database to store vectors and chunk content (I'm using Chroma because it's easy to configure locally and I have prior experience, but for a production environment it might be more appropriate to evaluate the tradeoffs of various vector dbs on the market).
We use FastAPI + MCP SDK to implement the mcp server endpoint. The FastAPI + MCP SDK combination allows for clean and fast implementation of everything needed for a base case like this.

#### Data collection seeding
I initially started using `docx2txt` for loading documents and `RecursiveCharacterTextSplitter` for chunking, but I noticed the text was being split into fairly arbitrary chunks. I then tried preloading them in md using `docx2md`, then using `MarkdownHeaderTextSplitter` to split the text based on headers. Checking manually, I noticed a more sensible split (confirmed by improved metrics using the `make eval` test).

We initially create a vector database seeding script from a folder containing the docx files that make up the KB:
1. Use docx2md to load file contents into markdown
2. Split documents using MarkdownHeaderTextSplitter, splitting on headers
3. Open the Chroma database connection and save the file contents
    - Persist data across runs
    - Save the source document name in the metadata — this could be useful for attesting the data used to respond to the client (even though in this case we are using locally saved sources that the client does not have direct access to)

#### Endpoint
A single endpoint needs to be implemented that receives the user's message and returns the relevant chunks:
1. Open the database connection
2. Perform a similarity search
3. Respond to the caller with the list of relevant chunks

#### Possible improvements
Documents can now be created, edited and deleted from the SQLAdmin panel (`http://localhost:8002/admin`): every change re-chunks and re-embeds the document and replaces its vectors in Chroma. Remaining gaps: the panel is unauthenticated, uploads are markdown/text rather than raw `.docx`, and re-embedding happens synchronously in the request.

### MCP User Server
The MCP User service is located in the `mcp_user_server` folder.
We use PostgreSQL as the database. Another possible alternative could have been sqlite, also very performant, though less expressive in the types offered. For this case it makes little difference either way. I'm not considering NoSql options as I believe a relational DB is well suited for modeling users and any personal information that might be added in the future, while maintaining good performance if the db is well modeled and indexed.
We use FastAPI + MCP SDK to implement the mcp server endpoint.
The endpoint requires no input parameters, as it relies on the user_id provided by the MCP Host, not on data generated by the model for the call, to determine which information to return:
1. Receives the request with API Key and user_id
2. Pre-filters results by user_id
3. Returns the obtained rows (actually just one row, having one row per user)

### CLI
A simple CLI tool, in the `chat_cli` folder, allows interfacing with the system, opening new chats or resuming existing ones. Ideally, a web app offering a chat UI should be implemented.

### Chat Backend Service
The chat service is located in the `chat_backend` folder.
The service is a FastAPI backend that, in addition to a login endpoint used just to simulate login by setting a cookie containing nothing but the user id, offers:
- an endpoint for listing messages of a chat, scoped by user
- an endpoint for creating new chats
- an endpoint for sending messages and receiving responses using SSE (chosen over WebSocket because we don't need true continuous bidirectional communication, but only that the server can stream the response once the client has sent its message)
We define the list of mcp servers from config, initially only the knowledge base and the mcp server for retrieving user information.
We also use PostgreSQL here to persist chat and agent data.
We implement a short term memory mechanism that compacts the chat content to safeguard the model's context (we set the compaction threshold from config), using SummarizationMiddleware.

#### Modeling
The models are as follows:
- Chat: associates users with messages and the model state used for that specific chat, also allowing the system to resume existing chats
    - The presence of the model associated with each chat could allow future implementation of metrics where individual models are evaluated based on some key chat values (as explained in the first section of this document)
- Messages: contains chat messages, with type ("agent" or "user") and message content indicated
    - We only save user and agent messages, not system prompts, tool calls and reasoning (these are saved by Langchain's short term memory system)
- AgentSettings: contains the settings of agents usable in chats (system prompt, summarization parameters, model name, etc.). This would eventually allow for an admin panel to customize agents and select the default one for chats.


#### Auth
Login of a given user is simulated by calling the /login endpoint, which sets a cookie in the response.
The other endpoints are therefore protected by a simple Middleware that for now only verifies the presence of the cookie, without actually validating it.
To prevent a user from accessing other users' data, we set on every request sent to the user MCP server, besides the authentication API Key (which for now we could consider always valid, skipping the check server-side), the user_id of the user making the request.
The MCP servers will ensure to pre-filter data with the received user_id, where necessary (e.g., the MCP server does not need to filter by user, as all documents are available for consultation by the agent, and therefore by the user), to segment them by user.


#### Model provider
We use OpenAI as the model provider, setting the API Key in the application settings.

#### Chat Flow
Each call to `create_agent` receives a checkpointer, a component of Langchain's short term memory system that allows resuming an existing chat by reloading the agent graph state.
Each chat is assigned a thread_id that serves to identify the checkpointer for that chat.
We allow the user to provide a thread_id when launching the chat service: if not provided, the client first creates a new chat on the backend and then starts sending messages; if instead the thread_id is provided, the client retrieves the message history from the backend and displays it in the CLI before continuing the conversation.

The backend therefore exposes two distinct endpoints for the chat lifecycle:
- `POST /chats` — creates the `Chat` record and links it to the default settings (`is_default = true`). Returns the `thread_id` to use for subsequent exchanges and for any future resumption.
- `POST /chats/{thread_id}/messages` — assumes the chat exists (404 if not) and simply invokes the agent. The agent settings are retrieved from the `AgentSettings` row already linked to the chat.

The actual flow, on the backend side, for each message is therefore:
1. Retrieve the user_id from the cookie and the thread_id from the path
2. Verify that the chat exists for that pair (user_id, thread_id), otherwise respond with 404
3. Resolve the agent parameters (`AgentParams`) from the settings linked to the chat
4. Save the user message to the database
5. Build the agent with the app-level shared checkpointer, adding tools via `MultiServerMCPClient`:
    1. Here, for example, the system prompt, summarizer, and model name to use are specified
    2. Here, the user_id is also set in the headers to send to MCP servers to authenticate calls and prevent leaks
6. Stream the agent's response tokens to the client via SSE (hiding any reasoning and tool calls)
7. Once streaming is complete, save the response message to the database


## Next steps
### Handling tools with write access to data
To allow the agent to make tool calls that modify data, one could consider adding dedicated MCP servers, and adding a verification layer with Human-in-the-loop, so that an operator can approve the various calls after reviewing them.

In practice, assuming we have a working web app where the chat is implemented via a WebSocket between the client and the backend where the agent runs, one could add a new tool to the MCP servers defined by MultiServerMCPClient, then define the approval methods by adding a HumanInTheLoopMiddleware, specifying in its config which tools need approval. When one of these tools is called, the agent pauses, and a message is sent to the user explaining that the agent is undertaking an action that requires operator approval. From this point on, the web socket waits for a notification to understand when to resume from the interrupted checkpoint. At the same time, a message is sent to a handler that creates notifications visible on a dashboard for operators, allowing real-time visibility of new interrupts and their triggering cause. The interrupt data sent in the message could include the chat's thread_id, so the dashboard can reconstruct the current chat situation with the client to give the operator full context. The operator can then decide whether to approve, reject, or possibly modify the tool call. Once the interrupt is resolved, the agent is notified to allow the client to resume the chat from where it left off.

### Adding a middleware for prompt injection prevention
Although newer models are well aligned to mitigate prompt injection attempts by users, it could be a good idea to add a Middleware where a dedicated model evaluates the message content, deciding whether to block it with a standard response message. Another, milder possibility could be to block messages containing certain keywords.

### Adding a middleware for PII prevention
Add a middleware that handles redacting any PII accidentally provided by the client to the model, so that when we save messages for chat persistence, they do not contain sensitive client data

### Admin backend panel
The backend could provide an admin or back-office interface where company operators can log in to monitor and intervene in customer chats (e.g., the interrupt dashboard case seen earlier).

### Auth
Since this is a system composed of multiple services, it might be a good idea to rely on JWT tokens to identify users, for example in communication between the chat service and the user mcp server. Each service can independently identify the user who made the call by validating the JWT.

### MCP tools configuration
Currently the tools are fixed and are added to the agent inside `chat_backend/src/chat_backend/mcp_servers.py`. It could be convenient to configure them from an admin panel, associating them with a particular agent in AgentSettings, to easily add new functionality to agents in chats and evaluate which mix of model + tools is best.

### Metrics
The system has good foundations for implementing metrics: each Chat is linked to a specific agent setup (AgentSettings). This data could be augmented by a system that collects context consumption, number of messages per chat, chat cost, customer satisfaction, then exporting them to an analytics db where queries can be run to better understand which setup is best for our needs.

### LLM-as-judge tests
It could be useful to set up a series of tests where an LLM evaluates, given certain predefined questions and possible ground truths or expected results, the effectiveness of a specific agent in answering those questions. These tests could be run every time a new setup is added to AgentSettings (so it would be a test to run in production rather than during development).
The test could evaluate:
- Given questions and expected answers, how well the actual answers adhere to the expected ones
- Given questions and the agent's answers, how well these satisfy the original question

The first case also requires having expected answers for each question, while the second case only requires questions.
A dataset of questions (and expected answers) could be created initially by domain experts who know the sector and interact with users, and then extended by collecting questions actually asked by users during system usage in production.
